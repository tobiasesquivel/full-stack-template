Registro y codegen

Al terminar podés mirar la lista de archivos de un PR y saber si al agente le faltó registrar el handler, mapear la ruta o correr codegen write.

La primera vuelve sobre la P5 de la lección 2, la que fallaste. La segunda es de "Revisar a un agente".

Repaso · Revisar a un agente

En GetUserTimezoneEndpoint, un agente escribió este control y en el handler no llamó a CanAccessAsync. ¿Qué recibe un Admin que pide la zona horaria de Alice?

if (user.GetCallerId() != authId)
    return Results.Forbid();

El if solo deja pasar al dueño. CanAccessAsync(quién, recurso, permiso) deja pasar al dueño y a quien tiene el permiso, como un Admin. Por eso el permiso se decide en el handler y no en el endpoint. Además, el handler lee primero el recurso: si no existe da 404, y recién después decide el 403.

Repaso · Revisar a un agente

Esta vez el agente sí anidó Handler dentro del record partial, pero puso las dos mitades en GetUserTimezoneQuery.cs. ¿Qué está mal?

La forma pide dos archivos: los campos en GetUserTimezoneQuery.cs y el handler en GetUserTimezoneQueryHandler.cs. DUNE0031 rompe el build si el handler no vive en <Mensaje>Handler.cs.

La idea

Una slice no se conecta sola. Su feature la anota en dos lugares: el handler para Wolverine y la ruta para ASP.NET. Además, Wolverine no arma el código que llama al handler mientras la app corre: lo genera un comando antes (codegen write) y ese código se versiona como cualquier archivo.

Dónde se enchufa GetUser

  1. Hosts/Monolith/Program.cs:23 y :48 El programa llama a AddUsersFeature() y a MapUsersEndpoints(). Esto ya existe: una slice nueva de Users no toca Program.cs.
  2. Features/Users/UsersFeature.cs:40 services.AddMediatorHandler<GetUser.GetUserQuery.Handler>(MediatorTransaction.None); anota el handler y su clase de transacción. La transacción la ves en la lección 7.
  3. Infrastructure/Messaging/MessagingExtension.cs:57 y :129 Wolverine tiene apagada la búsqueda automática de handlers (DisableConventionalDiscovery). Solo conoce los que la feature anotó, y los suma uno por uno con IncludeType. Sin la línea 40, Wolverine no sabe quién atiende GetUserQuery.
  4. Features/Users/UsersFeature.cs:62 GetUser.GetUserEndpoint.Map(users); registra las rutas dentro del grupo /users, el que exige sesión. Sin esta línea la ruta no existe, y el pedido da 404.

El código generado

Wolverine no tiene un código fijo que sirva para cualquier handler. Escribe una clase C# por handler que hace todo el trabajo: pide las dependencias, crea el handler y llama a Handle. Su documentación da la razón: "we needed to reduce object allocations, layering, runaway Exception stack traces" (Wolverine, Code Generation).

// Hosts/Monolith/Internal/Generated/WolverineHandlers/GetUserQueryHandler899234218.cs
var usersDbContext = GetRequiredService<UsersDbContext>(...);       // línea 29
var getUserQuery = (GetUserQuery)context.Envelope.Message;          // línea 31
var handler = new GetUserQuery.Handler(usersDbContext, authModule);   // línea 40
var outgoing1 = await handler.Handle(getUserQuery, cancellation);   // línea 43

Recortado. El new del handler está escrito en un archivo del repo: si cambia el constructor del handler, este archivo queda viejo.

Ese código existe porque el repo usa TypeLoadMode.Static (MessagingExtension.cs:56). Static = "Never generate types at runtime, but instead try to locate the generated types from the main application assembly": nunca generar mientras corre, solo buscar lo ya generado (misma fuente). Por eso alguien tiene que generarlo antes, con este comando:

dotnet run --project backend/Hosts/Monolith/TemplateApp.csproj -- codegen write

El comando escribe backend/Hosts/Monolith/Internal/Generated/WolverineHandlers/: una clase por handler y GeneratedHandlerRegistry.cs, la lista de handlers que Wolverine conoce. El .csproj compila esa carpeta (TemplateApp.csproj:15).

Codegen (generación de código) = una plantilla que se completa una vez, antes de usarla. Wolverine arma la clase que llama a cada handler; vos la guardás en git y la revisás como cualquier archivo.

Quién avisa si quedó viejo

Wolverine no se da cuenta solo: "Nothing in Wolverine is able to detect that the generated source code needs to be rewritten" (Wolverine, Code Generation). Lo detecta el gate dune/gates/check-codegen.mjs: corre codegen write, mira con git si algo cambió y, si cambió, falla con el mensaje "corré dotnet run ... codegen write y versioná el resultado". Corre en CI y en check-all.

Por qué así

Con el modo Static, la app no compila código mientras corre: no necesita el compilador de C# en producción (docs/decisions.tsv, fila del 2026-11-19). Y como el código generado está en git, lo que Wolverine hace alrededor de cada handler se lee y se revisa en el PR. Apagar la búsqueda automática hace que cada handler declare su clase de transacción en una línea visible.

En la industria: Wolverine trae por defecto la búsqueda automática y el modo Dynamic, que genera el código la primera vez que se usa cada handler. Fijar Static y versionar lo generado es la opción para no compilar en producción.

Qué mirar cuando un agente toca esto

  • Un handler nuevo suma su línea AddMediatorHandler en <Feature>Feature.cs, y su endpoint, su línea Map. Si el PR no toca <Feature>Feature.cs, falta el enchufe.
  • Un handler nuevo, o un cambio en el constructor de uno, trae cambios en Internal/Generated/. Si no hay, el agente no corrió codegen write.
  • Nadie edita Internal/Generated/ a mano. Si el diff muestra un cambio ahí sin un cambio en un handler, preguntá de dónde salió.

Recordar

3. ¿Por qué hace falta la línea AddMediatorHandler?

La búsqueda automática está apagada (DisableConventionalDiscovery, MessagingExtension.cs:57). Wolverine conoce solo los handlers que cada feature anota.

Revisar a un agente

4. Un agente le sumó al constructor de GetUserQuery.Handler un parámetro TimeProvider clock y no corrió codegen write. ¿Qué pasa?

El archivo generado tiene escrito new GetUserQuery.Handler(usersDbContext, authModule) con dos argumentos, y se compila con el resto del host. Con un constructor de tres parámetros, ese new ya no compila. Lo arregla correr codegen write.

Revisar a un agente

5. Para no correr el comando, un agente editó a mano GetUserQueryHandler899234218.cs y agregó el argumento que faltaba. Compila. ¿Qué pasa en el PR?

check-codegen corre codegen write, que pisa el archivo con lo que genera Wolverine, y falla si git ve una diferencia con lo commiteado. Una edición a mano casi nunca coincide con eso. Además, la convención es que nadie lo edita a mano.
