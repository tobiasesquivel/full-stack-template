El recorrido de un pedido

Al terminar podés seguir un GET /api/v1/users/me desde el navegador hasta la base y de vuelta, y detectar si un agente se salteó un tramo.

La idea: el endpoint no llama al código que resuelve el pedido. Arma un mensaje (la query) y se lo entrega a un intermediario, Wolverine, que busca quién lo atiende y le devuelve la respuesta.

Los seis tramos, con su archivo

  1. Hosts/Monolith/Program.cs:48 → Features/Users/UsersFeature.cs:60-62 Al arrancar, Program.cs registra las rutas de Users. El grupo /users exige sesión (RequireAuthorization()), entonces sin cookie el pedido corta acá con un 401.
  2. Features/Users/GetUser/GetUserEndpoint.cs:13-18 ASP.NET llama al método del endpoint y le pasa lo que pide su firma: el usuario de la sesión (ClaimsPrincipal), el bus (IMessageBus) y el aviso de cancelación (CancellationToken). Microsoft lo llama parameter binding (enlazar cada parámetro con su origen).
  3. GetUserEndpoint.cs:25-26 El endpoint arma new GetUserQuery(callerId, authId) y lo entrega con bus.InvokeAsync(...). No conoce al handler: solo conoce el mensaje.
  4. Hosts/Monolith/Internal/Generated/WolverineHandlers/GetUserQueryHandler899234218.cs:40-43 Wolverine busca el handler de GetUserQuery, lo crea con sus dependencias y llama a Handle, en el mismo proceso y en ese momento. Doc de Wolverine: "This execution happens inline".
  5. Features/Users/GetUser/GetUserQueryHandler.cs:25-38 El handler lee el perfil, revisa el permiso, le pide la cuenta a Auth y devuelve un ErrorOr (una caja que trae el valor o un error).
  6. Shared/Http/ApiResults.cs:7-34 De vuelta en el endpoint, ApiResults.ToResult traduce la caja a HTTP: valor da 200, Forbidden da 403 y NotFound da 404.

Mediator (el patrón que cumple IMessageBus acá) = un mostrador de pedidos. El endpoint deja el pedido en el mostrador y no sabe quién cocina. Wolverine se lo pasa al cocinero (el handler) y le devuelve el plato al endpoint.

Por qué así

Como el endpoint no conoce al handler, el handler se prueba sin HTTP. Además Wolverine envuelve a todos los handlers con las mismas reglas, como la transacción, porque todos pasan por el mostrador. El repo lo eligió también para aprender el patrón (AGENTS.md: "Un patrón del plan se aplica aunque Tasks no lo necesite").

En la industria: en .NET el mediator más usado es MediatR, y InvokeAsync de Wolverine es su equivalente directo (Jeremy Miller, autor de Wolverine). Para código nuevo, el equipo de Wolverine prefiere sus propios endpoints (Wolverine.HTTP) sobre el mediator detrás de una minimal API.

Qué mirar cuando un agente toca este recorrido

  • El endpoint entrega un mensaje con bus.InvokeAsync. Si hace new ...Handler(...), se salteó el mostrador.
  • El handler devuelve ErrorOr<T>, y el endpoint lo pasa por ApiResults.ToResult. Si arma los status a mano, puede confundir un 403 con un 404.

Practicá: recordá sin mirar

Respondé sin volver a leer arriba. Equivocarte acá ayuda a recordar.

Recordar

1. ¿Quién llama al método Handle del handler?

El endpoint solo entrega el mensaje. La clase que generó Wolverine crea el handler y llama a Handle (tramo 4).

Revisar a un agente

2. Un agente agregó GetUserTimezone. ¿Qué está mal en su endpoint?

var handler = new GetUserTimezoneQuery.Handler(db, auth);
var result = await handler.Handle(query, ct);
return ApiResults.ToResult(result, value => Results.Ok(value));

Crea el handler a mano, entonces se saltea el mostrador y las reglas que Wolverine pone alrededor de cada handler. Lo correcto es bus.InvokeAsync<ErrorOr<T>>(query, ct).

Recordar

3. ¿De dónde saca el endpoint el IMessageBus que recibe?

ASP.NET completa cada parámetro según su origen. Un servicio como el bus sale del contenedor de dependencias (tramo 2).

Revisar a un agente

4. Otro agente hizo que el handler devuelva UserResponse? y que el endpoint haga esto. ¿Qué se pierde?

return result is null ? Results.NotFound() : Results.Ok(result);

Un null no dice por qué falló. Con ErrorOr, el handler distingue "no existe" (404) de "no te dejo verlo" (403), y ApiResults además manda el code del error.

Recordar

5. En el diagrama, ¿quién convierte el ErrorOr en 200, 403 o 404?

El handler no sabe de HTTP. El endpoint llama a ApiResults.ToResult (tramo 6).
