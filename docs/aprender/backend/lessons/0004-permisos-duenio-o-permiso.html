Permisos: dueño o permiso

Al terminar podés predecir quién pasa y quién recibe 403 en cada slice de Users, y ver por qué un if que compara ids deja afuera a alguien.

Repaso

Dos preguntas de "Revisar a un agente" de lecciones anteriores. La de permisos que fallaste dos veces es el tema de hoy: vuelve al final, con una forma nueva.

Repaso · Revisar a un agente

Un agente sacó del constructor de un handler un parámetro que ya no usaba, y no corrió codegen write. ¿Qué pasa?

El archivo generado sigue llamando al constructor viejo, con un argumento de más. Ese new ya no compila. Pasa lo mismo al sacar un parámetro que al agregarlo: cualquier cambio de constructor pide codegen write.

Repaso · Revisar a un agente

Un agente movió UserResponse de Users/Contracts/ a Users/GetUser/ "porque es la respuesta de GetUser". ¿Qué se rompe?

OpenSession y RegisterUser, de Auth, devuelven UserResponse. Una feature solo puede usar el Contracts/ de otra (DUNE0004), así que fuera de Contracts/ Auth no compila.

La idea

Un permiso sobre un recurso se decide con dos preguntas, en este orden: ¿es el dueño? Si no, ¿tiene el permiso? El if que compara ids hace solo la primera. Y la decisión va en el handler porque recién ahí se conoce el recurso: quién es su dueño, y si existe.

401 ≠ 403. 401 = "no sé quién sos": no hay sesión, y lo corta el grupo /users con RequireAuthorization() antes de llegar al endpoint. 403 = "sé quién sos y no podés tocar esto": lo decide el handler, recurso por recurso.

Las dos preguntas, en el código

// Features/Auth/Access/AccessPolicy.cs:37-47
public async Task<bool> CanAccessAsync(string callerId, IOwnedResource resource, string permission, ...)
{
    if (string.Equals(callerId, resource.OwnerId, StringComparison.Ordinal))
        return true;                                          // 1. ¿es el dueño?

    return await HasPermissionAsync(callerId, permission, ct);  // 2. ¿tiene el permiso?
}

Users no ve esta clase: la llama por su puerta, IAuthModule.CanAccessAsync (Auth/Contracts/IAuthModule.cs:9).

De dónde sale "tiene el permiso"

Cada rol trae una lista fija de permisos (Features/Auth/Access/RolePermissions.cs:86-113). Para Users:

RolUsers.Read (ver perfil o cierre ajeno)Users.Manage (cerrar cuenta ajena)
Usernono
Adminsíno
SuperAdminsísí

Cada handler elige qué permiso pide. GetUser pide Read (GetUserQueryHandler.cs:31); DeleteUser pide Manage (DeleteUserCommandHandler.cs:55). Por eso un Admin ve el perfil de Alice pero no puede cerrar su cuenta. El dueño pasa siempre, en los dos: la primera pregunta no mira roles.

Por qué el if del endpoint falla

El if (user.GetCallerId() != authId) return Results.Forbid(); parece seguro porque cubre al dueño. Hace la primera pregunta y se saltea la segunda, y además corre antes de leer el recurso. Así responde GET /api/v1/users/{id} en cada caso:

Las dos filas rojas las cubre GetUserTests.ForeignProfile_IsForbidden_WithoutPermission_Then_AllowedWithPermission: espera 404 para el id inexistente y 200 después de darle a Bob el rol Admin.

A veces el endpoint ni siquiera puede comparar

La ruta de un cierre es GET /users/closures/{closureId} (GetAccountClosureEndpoint.cs:11). La URL trae el id del cierre, no el de su dueño. El dueño aparece recién cuando el handler lee la fila de la base (GetAccountClosureQueryHandler.cs:41). Antes de leer, no hay nada contra qué comparar.

IOwnedResource y ClosureOwner

CanAccessAsync no pide un perfil: pide cualquier cosa con dueño. IOwnedResource = "algo que tiene dueño", y exige una sola propiedad, OwnerId (Shared/Domain/IOwnedResource.cs:3-6). UserProfile la implementa (Users/Domain/UserProfile.cs:6). Un cierre no es una entidad con esa interfaz: el handler tiene solo el id del dueño. Entonces lo envuelve en new ClosureOwner(ownerId), un record de una línea (Users/Access/ClosureOwner.cs), y se lo pasa a CanAccessAsync (GetAccountClosureQueryHandler.cs:42).

Por qué así

Microsoft lo explica para ASP.NET Core: "Attribute evaluation occurs before data binding and before execution of any method that loads a resource. Declarative authorization with an [Authorize] attribute doesn't suffice for resource-based authorization." Lo que depende del recurso se decide en el código que lo cargó, y en este repo ese código es el handler.

En la industria: ASP.NET Core lo hace con IAuthorizationService.AuthorizeAsync(user, resource, policy), llamado después de cargar el recurso. El repo usa su propia puerta, IAuthModule.CanAccessAsync, porque Users solo puede hablar con Auth por Contracts/.

Qué mirar cuando un agente toca esto

  • Todo handler que lee o cambia algo con dueño llama a CanAccessAsync después de leerlo y antes de devolverlo o cambiarlo. Si falta, cualquiera con sesión lo ve.
  • Un if que compara CallerId con un id, en el endpoint o en el handler, se saltea la segunda pregunta. Pedí CanAccessAsync.
  • El permiso correcto: Read para ver, Manage para cambiar o cerrar. Si el agente cambia uno por otro, mirá la tabla de roles: cambia quién pasa.

Practicá: recordá sin mirar

Respondé sin volver a leer arriba. Equivocarte acá ayuda a recordar.

Recordar

1. ¿Qué dos preguntas hace CanAccessAsync, en orden?

Primero compara callerId con OwnerId; si no coinciden, busca el permiso en los roles (AccessPolicy.cs:43-46). La sesión la mira antes el grupo /users, y si el recurso existe lo mira antes el handler.

Revisar a un agente

2. Un agente quiere frenar en el endpoint de GET /users/closures/{closureId} a quien no es dueño del cierre. ¿Por qué no puede hacerlo bien ahí?

La URL trae el id del cierre. Quién es el dueño se sabe recién al leer la base, y eso pasa en el handler. El endpoint sí tiene la sesión (ClaimsPrincipal), pero no tiene con qué compararla.

Recordar

3. Bob tiene rol Admin. ¿Qué puede hacer con la cuenta de Alice?

Admin tiene Users.Read pero no Users.Manage (RolePermissions.cs). GetUser pide Read y DeleteUser pide Manage. Para cerrar una cuenta ajena hace falta SuperAdmin.

Revisar a un agente

4. En DeleteUserCommandHandler, un agente cambió UserPermissions.Manage por UserPermissions.Read. ¿Qué cambia?

Admin tiene Read, así que ahora pasa la segunda pregunta en DeleteUser. Alice sigue pasando por la primera: es la dueña.

Revisar a un agente

5. Esta vez el agente puso el control en el handler, como primera línea de Handle. ¿Qué sigue mal?

if (query.CallerId != query.AuthId)
    return UserErrors.Forbidden;

El lugar ya es el correcto, pero la regla sigue a medias: compara ids y se saltea "¿tiene el permiso?", así que el Admin recibe 403. Además corre antes de leer el perfil: un id que no existe da 403 en vez de 404. Lo correcto es leer, dar 404 si no está y después llamar a CanAccessAsync.

Fuente principal Microsoft Learn: "Resource-based authorization in ASP.NET Core". Leé la introducción y "Use imperative authorization": son 5 minutos. Los ejemplos son de Blazor, pero la idea es la misma: se autoriza después de cargar el recurso.
