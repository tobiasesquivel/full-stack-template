Un command: Request, Command y validador

Al terminar distinguís lo que manda el navegador (*Request) del mensaje que viaja por el bus (*Command), y sabés quién valida y qué 400 sale.

Repaso · Revisar a un agente

Un agente renombró el code "Project.NameTaken" a "Project.DuplicateName". Todos los tests del backend pasan. ¿Qué se rompe?

project-error.ts busca el texto exacto 'Project.NameTaken' para mostrar "Ya tienes un proyecto con ese nombre.". Con el código nuevo no lo encuentra y el aviso desaparece. El backend no se entera: por eso "un código publicado no cambia".

La idea

Una escritura tiene tres piezas. El Request = lo que manda el navegador en el cuerpo JSON. El Command = el mensaje que viaja por el bus: el Request más CallerId (quién pide), que el endpoint saca de la sesión. El validador = las reglas de forma del Command, y Wolverine lo corre antes del handler.

Las tres piezas en UpdateProfile/

  1. UpdateProfile/UpdateProfileRequest.cs:3 record UpdateProfileRequest(string DisplayName, string Timezone). Es el cuerpo del PUT /users/me: ASP.NET lo arma desde el JSON (lo viste en la lección 1 como parameter binding).
  2. UpdateProfile/UpdateProfileEndpoint.cs:19 new UpdateProfileCommand(user.GetCallerId(), request.DisplayName, request.Timezone). El endpoint copia los dos campos y suma CallerId (quién pide) desde la cookie.
  3. UpdateProfile/UpdateProfileCommandValidator.cs:10-22 Dos reglas: DisplayName entre 1 y el máximo de UserProfile, y Timezone una zona horaria IANA válida, como America/Argentina/Buenos_Aires. Usa FluentValidation (AbstractValidator<T>).
  4. Users/UsersFeature.cs:45 El validador se registra a mano, al lado de su handler. El repo configura Wolverine con UseFluentValidation(RegistrationBehavior.ExplicitRegistration) (MessagingRegistration.cs:26): no busca validadores solo.
  5. Hosts/Monolith/Internal/Generated/WolverineHandlers/UpdateProfileCommandHandler156792017.cs:45 El código generado llama al validador antes de crear el handler. El de GetUser no tiene esa línea: su query no tiene validador.

Por qué el Request no trae CallerId

Todo lo que viene en el JSON lo escribe el cliente, y puede mentir. Si CallerId viniera en el cuerpo, Bob mandaría el id de Alice y editaría el perfil de ella. Por eso quién pide sale siempre de la sesión, nunca del cuerpo. Por la misma razón, UpdateProfile no llama a CanAccessAsync: el Command no tiene a quién apuntar fuera de CallerId, así que solo puede tocar el perfil propio.

Request = el formulario que llena el cliente. Command = ese formulario con el sello de quién lo firmó, puesto por el sistema. En una lectura sin cuerpo, como GetUser, no hay formulario: el endpoint arma la query directo. Eso responde tu primera pregunta del curso.

Qué pasa cuando no valida

El validador falla, Wolverine tira una ValidationException, y ValidationExceptionHandler (Infrastructure/Http/ValidationExceptionHandler.cs:10-16) la convierte en errores de tipo Validation y se los pasa a ApiResults. Sale el mismo 400 de la lección 5, con un mapa de errores por campo:

HTTP/1.1 400 Bad Request
{
  "status": 400,
  "errors": { "Timezone": ["Timezone must be a valid IANA timezone."] },
  "code": "Validation.Failed",
  …
}

Recortado. ApiResults.cs:18-22 agrupa por el nombre del campo, que es el code de cada error de validación. UpdateProfileTests lo prueba mandando timezone = "No/Existe" y esperando un 400.

El validador revisa la forma de la entrada. El handler revisa el estado: si el perfil existe (404) o si un cierre se puede cancelar (409). La regla del repo: "Toda validación de entrada va en <Mensaje>Validator.cs, no en el handler" (docs/conventions.md:10).

Por qué así

Separar Request y Command deja el contrato HTTP en un lugar y el mensaje interno en otro: el frontend usa *Request con los mismos nombres, y el Command puede sumar datos que el cliente no elige. Con el validador como paso de Wolverine, ningún handler recibe un Command con forma inválida, y todos los 400 salen con el mismo formato.

En la industria: FluentValidation es la librería de validación más usada en .NET. Con MediatR se corre en un pipeline behavior; con Wolverine, en su middleware. La idea es la misma: validar antes del handler, una vez para todos.

Qué mirar cuando un agente toca esto

  • Un *Request nunca trae CallerId ni nada que diga "quién soy". Si aparece en el cuerpo, cualquiera se hace pasar por otro.
  • Un validador nuevo suma su línea AddSingleton<IValidator<…Command>, …Validator>() en <Feature>Feature.cs, y el código generado de su handler llama a FluentValidationExecutor. Si falta cualquiera de las dos, revisá que el validador realmente corra.
  • Un if que revisa largo, formato o nulos dentro del handler va al validador.

Recordar

1. ¿Qué campo tiene UpdateProfileCommand que no tiene UpdateProfileRequest?

El endpoint suma CallerId (quién pide) desde la sesión (UpdateProfileEndpoint.cs:19). AuthId no está en ninguno: el Command solo puede tocar el perfil de quien pide.

Revisar a un agente

2. Un agente sumó string CallerId a UpdateProfileRequest, y el endpoint ahora arma el Command con request.CallerId. ¿Qué está mal?

El cuerpo lo escribe el cliente. Bob manda el id de Alice en CallerId y el handler edita el perfil de Alice, sin ningún control de permisos que lo frene. Quién pide sale de la sesión: user.GetCallerId().

Recordar

3. ¿Quién corre UpdateProfileCommandValidator antes del handler?

La línea 45 del handler generado llama a FluentValidationExecutor antes de crear el handler. El endpoint solo arma el Command y lo entrega.

Revisar a un agente

4. Un agente agregó esto al principio de UpdateProfileCommand.Handler.Handle. ¿Qué cambiarías?

if (command.DisplayName.Length > UserProfile.DisplayNameMaxLength)
    return UserErrors.InvalidDisplayName;

El largo es forma de la entrada: va en UpdateProfileCommandValidator, que ya lo revisa con UserProfile.IsValidDisplayName (línea 14). El handler revisa estado, no forma.

Revisar a un agente

5. Un agente creó ChangeEmailCommandValidator, registró el handler y corrió codegen write, pero no registró el validador. En el generado de su handler no aparece FluentValidationExecutor. ¿Qué pasa con un email inválido?

Con ExplicitRegistration, Wolverine usa solo los validadores registrados. El generado lo muestra: no hay ninguna línea que llame al validador, así que el Command entra al handler tal como vino. Falta AddSingleton<IValidator<ChangeEmailCommand>, ChangeEmailCommandValidator>().
