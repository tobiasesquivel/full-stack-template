Errores: ErrorOr y ApiResults

Al terminar podés predecir el status y el code de cada error de una slice, y notar cuando un agente inventa un error fuera del catálogo o cambia un código que ya usa el frontend.

Repaso

Las dos preguntas que fallaste en la lección 4, con otra forma.

Repaso · Recordar

¿Por qué falla el build si cambiás el constructor de un handler (agregás o sacás un parámetro) y no corrés codegen write?

El archivo de Internal/Generated/ tiene escrito new Handler(a, b) con los argumentos del constructor viejo. Si ahora el constructor pide uno, o tres, ese new no coincide y C# no lo compila. Sacar un parámetro rompe igual que agregarlo.

Repaso · Recordar

WithdrawAccountClosureCommandHandler.cs:51 llama a CanAccessAsync(command.CallerId, new ClosureOwner(ownerId), UserPermissions.Manage, ct). Bob tiene rol Admin. ¿Puede cancelar el cierre de cuenta de Alice?

Bob no es el dueño, así que cuenta la segunda pregunta: ¿tiene Users.Manage? Admin tiene solo Users.Read (RolePermissions.cs). Pasan Alice, por dueña, y un SuperAdmin, por permiso. "Solo el dueño" es falso: el SuperAdmin también pasa.

La idea

El handler no tira excepciones ni elige status HTTP: devuelve un error de su catálogo (UserErrors.cs) dentro de un ErrorOr. ApiResults mira el tipo del error para elegir el status, y copia su código en la respuesta. El frontend decide qué mostrar por ese código.

Un error tiene dos partes que importan

// Features/Users/UserErrors.cs:16-18
public static Error ClosureNotCancellable(Guid closureId) => Error.Conflict(
    code: "User.ClosureNotCancellable",
    description: $"Account closure '{closureId}' already started or ended: ...");
  • El tipo (Error.Conflict) decide el status. Lo traduce ApiResults.StatusFor (Shared/Http/ApiResults.cs:25-34).
  • El código ("User.ClosureNotCancellable") viaja en el cuerpo como code (ApiResults.cs:36). El texto de description sale como title, pero es para personas: puede cambiar.

ErrorOr = una caja que trae el valor o uno o más errores, nunca los dos. El handler devuelve la caja; quien la recibe pregunta IsError y no necesita un try/catch (ErrorOr en GitHub).

Un handler, tres errores en orden

WithdrawAccountClosure (cancelar un cierre de cuenta durante el período de gracia) muestra el orden completo, el mismo de la lección 4 más un paso:

  1. WithdrawAccountClosureCommandHandler.cs:48-49 Busca de quién es el cierre. Si no lo encuentra: ClosureNotFound → 404.
  2. WithdrawAccountClosureCommandHandler.cs:51-52 CanAccessAsync con CallerId (quién pide) y el permiso Manage. Si no pasa: Forbidden → 403.
  3. WithdrawAccountClosureCommandHandler.cs:58-59 Le pide al perfil que retire el cierre. Si ya arrancó o terminó: ClosureNotCancellable → 409.

Si Alice cancela un cierre que ya arrancó, recibe:

HTTP/1.1 409 Conflict
{
  "title": "Account closure '…' already started or ended: only a scheduled closure can be cancelled.",
  "status": 409,
  "code": "User.ClosureNotCancellable",
  …
}

Recortado: Results.Problem arma el cuerpo con statusCode, title y la extensión code (ApiResults.cs:11).

Por qué el code y no el title

El frontend elige el mensaje por code: frontend/src/app/features/projects/projects/project-error.ts:4-18 tiene un mapa de 'Project.NameTaken' a "Ya tienes un proyecto con ese nombre.". Por eso la regla es "Un código publicado no cambia" (docs/conventions.md:81). El title se puede reescribir sin romper a nadie.

Dónde nace un error

Solo en un catálogo: <Feature>Errors.cs en la raíz de la feature, o Shared/Http/HttpErrors.cs para lo que no es de ninguna feature. El código empieza con el nombre de la feature: UserErrors → User.. DUNE0014 rompe el build si un Error.Conflict(...) aparece en otro archivo, o si el prefijo no coincide. Los errores de validación son la excepción al prefijo: usan el nombre del campo. Los ves en la lección 6.

Por qué así

Un error esperado ("ese cierre ya arrancó") no es una excepción: es una respuesta posible del caso de uso. Con ErrorOr, la firma del handler lo dice (Task<ErrorOr<T>>) y el compilador obliga a mirar los dos caminos. Con un solo traductor, cada Conflict del repo da 409 con el mismo formato (conventions.md:80: "ApiResults es el único mapeo de Error a HTTP").

En la industria: el cuerpo con type, title, status y extensiones como code es el estándar Problem Details (RFC 9457), y Results.Problem de ASP.NET Core lo arma. Muchos proyectos .NET usan excepciones y un middleware que las traduce; ErrorOr es la variante "resultado" de esa idea.

Qué mirar cuando un agente toca esto

  • Un error nuevo nace en <Feature>Errors.cs con su prefijo. Un Error.X(...) en un handler o un throw para un caso esperado está fuera de la regla.
  • El tipo elige el status: un "ya existe" o "estado no permite" es Conflict (409), un "no está" es NotFound (404). Si el tipo está mal, el status sale mal aunque el código sea correcto.
  • Un PR que cambia el texto de un code existente rompe al frontend. Si hace falta otro motivo, va un código nuevo.

Practicá: recordá sin mirar

Respondé sin volver a leer arriba. Equivocarte acá ayuda a recordar.

Recordar

1. ¿Qué status sale de un error creado con Error.Conflict?

ApiResults.StatusFor traduce Conflict a 409. El 422 existe en el repo, pero sale de un Error.Custom con ese número (IdempotencyKeyReused).

Revisar a un agente

2. En un handler de Users, un agente escribió esta línea. ¿Qué está mal?

return Error.Conflict("Closure.AlreadyStarted", "The closure already started.");

Un error nace solo en UserErrors.cs, y su código empieza con User.. DUNE0014 rompe el build por las dos cosas. Además ya existe UserErrors.ClosureNotCancellable para ese caso.

Revisar a un agente

3. Un agente del frontend muestra un aviso así cuando falla cancelar un cierre. ¿Qué cambiarías?

if (problem.title.includes('already started')) {
  this.notice.set('El cierre ya arrancó.');
}

El title es texto para personas y puede cambiar. El contrato es code: problem.code === 'User.ClosureNotCancellable', como hace project-error.ts.

Recordar

4. Bob, con rol User, intenta cancelar un cierre con un closureId que no existe. ¿Qué recibe?

El handler busca el cierre primero (línea 48). Si no existe, corta con 404 antes de mirar permisos: sin cierre no hay dueño contra quién comparar. Primero 404, después 403.

Revisar a un agente

5. Un agente cambió "User.ClosureNotCancellable" por "User.ClosureAlreadyStarted" "para que sea más claro". ¿Qué está mal?

El frontend y cualquier otro cliente deciden por ese texto exacto. Cambiarlo rompe a quien ya lo usa, aunque el status siga siendo 409. Si hace falta un motivo distinto, va un código nuevo.
