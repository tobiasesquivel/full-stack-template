Los archivos de una slice

Al terminar sabés qué hace cada archivo de GetUser/ y notás cuándo un agente puso algo en el archivo equivocado.

Repaso de la lección 1

Dos preguntas antes de empezar. Acertaste todo, así que son de "Revisar a un agente", con una vuelta nueva.

Repaso · Revisar a un agente

Un agente no crea el handler con new: lo pide como parámetro del endpoint. ¿Qué está mal?

private static async Task<IResult> HandleAsync(
    Guid id, GetProjectQuery.Handler handler, CancellationToken ct)
{
    var result = await handler.Handle(new GetProjectQuery(id), ct);
    return ApiResults.ToResult(result, value => Results.Ok(value));
}

Pedir el handler como parámetro también saltea el mostrador: el endpoint llama a Handle sin pasar por Wolverine. docs/conventions.md (sección HTTP) lo prohíbe: el endpoint no recibe ni construye el handler, y despacha con bus.InvokeAsync. Lo hace cumplir DUNE0028.

Repaso · Revisar a un agente

En el handler de GetUser, un agente cambió return UserErrors.Forbidden; por return UserErrors.NotFound(query.AuthId);. ¿Qué recibe Bob al pedir el perfil de Alice?

ApiResults traduce lo que recibe y no adivina el motivo: NotFound da 404 aunque la causa real sea el permiso. El test ForeignProfile_IsForbidden_WithoutPermission_Then_AllowedWithPermission lo atrapa porque espera un 403.

La idea

Una slice = una carpeta por caso de uso, con un archivo por pieza. Cada archivo hace una sola cosa: el mensaje, quien lo atiende, la puerta HTTP y la prueba. Lo que usa otra feature sale de la carpeta y va a Contracts/.

Slice = una porción vertical de la torta. Atraviesa todas las capas (HTTP, lógica y base), pero solo para un caso de uso. El nombre viene de Jimmy Bogard.

Qué hace cada archivo

  1. GetUser/GetUserQuery.cs:3 Una sola línea: internal sealed partial record GetUserQuery(string CallerId, string AuthId);. Son los datos del pedido, sin comportamiento. AuthId = de quién es el perfil que se pide. CallerId = quién lo pide.
  2. GetUser/GetUserQueryHandler.cs:10-40 La otra mitad del mismo record, con la clase Handler adentro. Lee el perfil (404 si no está), decide el permiso (403 si no lo tiene), le pide la cuenta a Auth y arma la respuesta. Toda la lógica del caso de uso vive acá.
  3. GetUser/GetUserEndpoint.cs:9-29 Una clase estática. Map registra dos rutas, /me y /{authId}, y las dos terminan en el mismo HandleAsync privado: arma la query, la entrega al bus y traduce el resultado. No decide nada.
  4. GetUser/GetUserTests.cs Tres pruebas contra la API real, con PostgreSQL en un contenedor de Docker (Tests/Support/Hosts/PostgresFixture.cs, con Testcontainers). Cubren 200, 401, 403 y 404.
  5. Contracts/UserResponse.cs La respuesta no está en la slice porque Auth también la usa: OpenSession y RegisterUser devuelven el mismo perfil al registrarse y al iniciar sesión.

Por qué la query está partida en dos archivos

partial = C# deja escribir un tipo en varios archivos, y el compilador junta las partes en un solo tipo (Microsoft Learn). El repo lo usa para resolver un choque entre dos reglas:

  • Un archivo, un tipo, en todo el repo (DUNE0010).
  • Wolverine solo acepta handlers públicos, pero el handler usa tipos internal, como UsersDbContext. Una clase pública suelta no compila con esas dependencias. Anidada dentro de un record internal, sí: hacia afuera sigue siendo interna (docs/conventions.md:12).

DUNE0031 vigila esa forma: el handler se llama Handler, vive en <Mensaje>Handler.cs y está anidado en un record que termina en Query (si solo lee) o en Command (si cambia algo). Si un agente se aparta, el build falla (dune/Dune.Analyzers/DuneDiagnostics.cs:463).

Por qué CallerId viaja en la query

El handler no ve HTTP: no tiene la cookie ni el ClaimsPrincipal. Entonces el endpoint copia en el mensaje quién pide (user.GetCallerId(), en GetUserEndpoint.cs:25), y el handler decide el permiso con ese dato: CanAccessAsync(query.CallerId, profile, UserPermissions.Read, ct) (GetUserQueryHandler.cs:31). El dueño pasa, y un Admin también. Así el handler se puede probar sin HTTP.

Por qué así

Cambiar "ver un usuario" toca una sola carpeta, y un agente que lee GetUser/ ve el caso entero sin saltar entre capas. Bogard lo resume así: "Minimize coupling between slices, and maximize coupling in a slice" (mínimo acople entre slices, máximo acople dentro de cada una). El repo lo fija en docs/adr/0004-vertical-slices-deep-modules.md.

En la industria: muchos proyectos .NET todavía ordenan por capa técnica (Controllers/, Services/, Repositories/). Vertical slices creció con MediatR, el mediator de Bogard.

Qué mirar cuando un agente toca esto

  • El handler está en <Mensaje>Handler.cs como public sealed class Handler, dentro del record partial. Una clase GetXHandler suelta, o en el mismo archivo que el record, está fuera de la forma.
  • Un tipo nuevo que usa una sola slice queda en su carpeta. Si el agente lo pone en Contracts/, preguntale qué otra feature lo usa.
  • El endpoint no decide: ni permisos ni "no existe". Un if con una regla del negocio en *Endpoint.cs va al handler.

Recordar

1. ¿Qué archivo declara los datos que viajan por el bus?

GetUserQuery.cs declara los campos del record: CallerId y AuthId. El otro archivo del record agrega el Handler, no datos.

Revisar a un agente

2. Un agente creó la slice GetUserTimezone con este único archivo, GetUserTimezoneQuery.cs. ¿Qué está mal?

internal sealed record GetUserTimezoneQuery(string CallerId, string AuthId);

public sealed class GetUserTimezoneHandler
{
    public Task<ErrorOr<TimezoneResponse>> Handle(
        GetUserTimezoneQuery query, CancellationToken ct) { ... }
}

Junta dos tipos en un archivo y deja al handler suelto. La forma es: el record partial en GetUserTimezoneQuery.cs y Handler anidado en GetUserTimezoneQueryHandler.cs. DUNE0010 rompe el build por los dos tipos.

Recordar

3. ¿Por qué CallerId viaja dentro de GetUserQuery?

El handler no tiene la sesión. El endpoint copia quién pide en el mensaje, y el handler lo usa en CanAccessAsync para decidir el permiso.

Revisar a un agente

4. Un agente creó TimezoneResponse para su slice nueva y la puso en Users/Contracts/. Solo la usa su endpoint. ¿Qué está mal?

Contracts/ guarda solo lo que usa otra feature. Una respuesta que usa una sola slice queda en la carpeta de esa slice. UserResponse está en Contracts/ porque Auth la usa. DUNE0015 rompe el build si ninguna otra feature usa un contrato.

Revisar a un agente

5. Un agente agregó este control en GetUserEndpoint.HandleAsync, antes de entregar la query. ¿Qué se rompe?

if (user.GetCallerId() != authId)
    return Results.Forbid();

El permiso lo decide el handler con CanAccessAsync: el dueño pasa y un Admin también. El if deja afuera al Admin y además corta antes de saber si el perfil existe (primero 404, después 403). Falla el test que le da el rol Admin a Bob y espera un 200.

Fuente principal Jimmy Bogard: "Vertical Slice Architecture". Son 5 minutos y explican por qué una carpeta por caso de uso en vez de una carpeta por capa.
