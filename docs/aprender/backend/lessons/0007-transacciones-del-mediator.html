Transacciones del mediator

Al terminar podés elegir entre Atomic, Eager y None al registrar un handler, y notar cuando un agente guarda a mano o elige una clase que guarda de más.

Repaso

Hiciste bien toda la lección 6, así que van dos de "Revisar a un agente" con una vuelta nueva.

Repaso · Revisar a un agente

Para PUT /users/{authId}/timezone, un agente armó el Command con el authId de la ruta como perfil a editar y CallerId (quién pide) de la sesión. El handler busca el perfil por AuthId y lo guarda. ¿Qué falta?

Ahora el Command sí apunta a un perfil que puede ser ajeno, así que vuelve la regla de la lección 4: leer el perfil (404 si no existe) y llamar a CanAccessAsync(CallerId, perfil, UserPermissions.Manage). Sin eso, Bob cambia la zona horaria de Alice. UpdateProfile no lo necesita porque solo usa /me.

Repaso · Revisar a un agente

En un PR con un validador nuevo, ¿qué dos cosas confirman que va a correr?

El repo registra validadores a mano (ExplicitRegistration): hace falta la línea AddSingleton<IValidator<…>, …>() en <Feature>Feature.cs. Y en Internal/Generated/, el handler del Command tiene que llamar a FluentValidationExecutor.

La idea

El handler cambia objetos, pero no guarda. Guarda el código generado de Wolverine, alrededor del handler. La clase con que registrás el handler (AddMediatorHandler<T>(MediatorTransaction.X)) decide cómo: si todo va en una transacción, y si un error del handler deshace lo que cambió.

Transacción = todo o nada. Varios cambios en la base se confirman juntos (commit) o se descartan juntos (rollback). Nunca queda la mitad.

Atomic, paso a paso en el código generado

  1. Generated/…UpdateProfileCommandHandler156792017.cs:37 using var crossContextTransaction = CrossContextTransaction.Begin(); abre un TransactionScope = una transacción "ambiente" que abarca todo lo que pase adentro, aunque sean dos DbContext.
  2. …:55 if (outgoing1.IsError) return; Si el handler devolvió un error (NotFound, Conflict…), sale sin guardar. Como nunca llegó a Complete(), al salir del using se revierte todo.
  3. …:64 y :72 Si no hubo error: SaveChangesAsync escribe lo que el handler cambió y Complete() confirma.

El test UpdateProfileTests.UpdateMe_WhenItFailsAfterTheProfileWasSaved_KeepsTheProfileAsItWas lo prueba: hace fallar la base justo después de guardar, y comprueba que el nombre nuevo no quedó.

Por qué None también guarda

En la lección 3 viste que el generado de GetUser llama a SaveChangesAsync. Con None, Wolverine guarda lo pendiente al final, sin transacción y sin el corte por error. En una lectura no hay nada pendiente, así que no escribe nada. En OpenSession sí: guarda el intento fallido de login aunque responda 401. Con Atomic, ese intento se perdería.

La slice no toca la transacción

Un handler registrado no abre, no confirma, no revierte y no llama a SaveChanges. DUNE0029 ("La slice no maneja la transacción") rompe el build si lo hace. La única excepción es guardar dentro de un try que traduce un DbUpdateException a un error del catálogo (CreateProject y UpdateProject, por el nombre de proyecto repetido).

Por qué así

Si cada handler guardara a mano, alguno se olvidaría de guardar, otro guardaría antes de un error y dejaría la mitad. Con la transacción en el código generado, la regla vive en un solo lugar y se ve en el PR: es la palabra Atomic, Eager o None en <Feature>Feature.cs.

En la industria: Wolverine trae su middleware transaccional para EF Core (Wolverine, EF Core Transactional Middleware); con MediatR se suele escribir un pipeline behavior que abre y confirma. El corte por ErrorOr de Atomic es propio de este repo.

Qué mirar cuando un agente toca esto

  • Un comando que escribe se registra Atomic, salvo que tenga una razón escrita para Eager (outbox de Wolverine, saga) o None (tiene que guardar aunque falle). Un comando nuevo con None pide esa razón.
  • Un SaveChangesAsync, BeginTransaction o TransactionScope dentro de un handler está fuera de la regla, salvo el try que traduce una restricción de la base.
  • Si cambia la clase de un handler, cambia su código generado: el PR trae cambios en Internal/Generated/.

Recordar

1. ¿Quién llama a SaveChangesAsync cuando corre UpdateProfile?

La línea 64 del handler generado. El handler solo cambia profile.DisplayName y profile.Timezone (UpdateProfileCommandHandler.cs:34-35) y devuelve la respuesta.

Revisar a un agente

2. Un agente agregó await _db.SaveChangesAsync(ct); al final de UpdateProfileCommand.Handler.Handle, "para asegurarse de que se guarde". ¿Qué está mal?

El generado ya guarda y confirma alrededor del handler. DUNE0029 rompe el build si la slice llama a SaveChanges. La única excepción es el try que traduce un DbUpdateException.

Recordar

3. Un handler registrado Atomic cambia el perfil y después devuelve UserErrors.NotFound. ¿Qué queda en la base?

if (outgoing1.IsError) return; sale antes de SaveChangesAsync y de Complete(), así que el TransactionScope se descarta sin confirmar.

Revisar a un agente

4. Un agente registró un comando nuevo que cambia el nombre de un proyecto con MediatorTransaction.None. El handler cambia el nombre y, en algunos casos, después devuelve un Conflict. ¿Qué riesgo hay?

Con None no hay corte por error: Wolverine guarda lo pendiente al final. El cliente recibe 409 y el nombre igual cambió. Un comando que escribe va Atomic.

Recordar

5. ¿Por qué OpenSession (el login) se registra con None y no con Atomic?

Un login fallido responde un error, y aun así el intento tiene que quedar guardado. Atomic lo descartaría con el corte por IsError.
